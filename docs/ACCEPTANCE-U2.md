## 0. 需要的人和群（先凑齐，否则跑不了）

| 记号 | 是什么 | 为什么要 |
|---|---|---|
| 群 A / 群 B | **两个**测试群，机器人都进去、都建好工作空间 | 绑定是跨群的东西，一个群验不出来 |

## 1. 证据槽 ①：双群绑定 —— 先 A 群、再 B 群 ⇒ 私聊看 B 群

**步骤**

1. 甲在 **A 群**发一句（@ 或不 @ 都行 —— 但必须真的发出去）。
2. 甲在 **B 群**发一句。
3. 甲在**私聊**发一条依赖归属的指令（如 `你想做哪一块` 或 `报告`）。

**期望 / 判据（三条都要看）**

- 私聊回话里的**来源标题是 B 群的作业书标题** —— 落点是 `allocation.render_task_list()` 的**首行**（对齐卡 #9：私聊回话也必须带）。
- `data-upgrade\index.json` 里 `user_last_group[甲的 open_id]` == **B 群的 chat_id**。
- **反向再验一次**：甲回 A 群发一句 → 再私聊 ⇒ 来源标题变成 **A 群**（证明是「最后一次胜出」，不是「首次绑定生效」）。

**留痕**：两群消息的时间戳 + 私聊那条 `recv` / `-> ` 行 + `index.json` 里该键的值。

## 2. 证据槽 ②：从没互动过 ⇒ `NEED_GROUP`

**为什么这一槽在 U2 之前跑不出来（开发实测，2026-09-16）**：现状 `NEED_GROUP` 全仓只有**一条**产点，挂在 `我想提议：` 这条路径上，判据是**全局** `state["group_chat_id"]` 为空（`router.route()` 里 `我想提议：` 那个分支）；而任何一次群消息都会把这个全局值写上 ⇒ 只要群里有人发过话，私聊提议**必然**被转发进群、`NEED_GROUP` 拿不到。穿透批 run2 实测印证：私聊提议被转发进群，私聊侧只回「已经匿名发到群里了。」（`docs\evidence\2026-09-16-u2-preflight-penetration.md` §3 第 ⑤ 行 / §4）。

**⇒ 这一条给 U2 定的范围（不只是为了这一槽）**

- 判据从**全局** `group_chat_id` 为空，换成「**该人无绑定**」（按人查 `user_last_group`）。
- **所有依赖归属的私聊指令**都要走这条判据 —— 否则别的指令仍会拿全局值去猜群。
- 只改 `我想提议：` 一条路径 = 这一槽**走不到分支**（这是开发实测挖出来的，别当成「改一行」）。

**步骤**

1. 丙在**私聊**发 `你想做哪一块`（或 `作业书`）。
2. 丙在**私聊**再发一条**别的**依赖归属的指令（如 `报告`）—— 同样要回 `NEED_GROUP`（证明判据是按人的、且覆盖多条指令，而不是只堵了 `我想提议：` 这一条）。

**顺序（PM 2026-09-16）**：**非成员 / 未绑定的一方先发，成员后发**（本槽 = **先丙、后甲**）—— 反过来，先发那条的静默会被「当时还没有可对照的活跃状态」解释掉 ⇒ **假阳性**。两条连着发，中间不插别的动作。

**期望 / 判据**

- 回 `NEED_GROUP` 那句话（「我还没认下群…」），**不落盘、不起 pipeline**。
- `index.json` 里**不出现**丙的 open_id —— 出现了就是错的（说明绑定是被猜出来的）。
- 日志里**没有** pipeline 启动行。

**留痕**：私聊 `recv` / `-> ` 行 + `index.json` 的相关片段。

> **同批的顺序纪律**（裸数字必须先有窗 / 摘人会改分母 / 非成员先发）见 §5 —— 同一台机器同一批人跑，别混。

## 3. 证据槽 ③：绑定写入的并发正确性

**步骤**：甲**同时**在 A 群、B 群各发一句（相隔 < 1 秒）→ 然后私聊。

**期望 / 判据**

- `index.json` 的最终值 ∈ {A, B}，且**与日志里「后到的那条群消息」的 chat_id 一致**（后到者胜出）。
- **不出现丢更新**：写盘走 `JsonStore.mutate_raw()` 的**锁内读-改-写**（§7.4 第 3 条）。
- **重复 5 轮**取一致；任一轮出现「日志后到的是 B、索引却是 A」即为 ❌。

**留痕**：每轮两条群消息的时间戳 + 每轮结束时的索引值。

## 4. 回归（对齐卡 #5）：`storage` 不再「没变化也写盘」

**为什么**：`mutate_raw()` / `mutate_many()` 原来是**无条件写盘**（fn 原样返回也会写）。U2 把它改成**锁内序列化比较：新值 == 旧值 ⇒ 不写盘**（**已落地 `5dcb019`**：`src\storage.py` 的 `mutate_raw()` / `mutate_many()` 走 `_write_if_changed_unlocked()`）。

**单测（主判据）**

- `mutate_raw(name, lambda doc: doc)`（**原样返回**）⇒ 文件**字节与 mtime 都不变**。
- 同一形状再测一次 `mutate_many`。

**手工步（交叉验证）**

1. 起实例，记下 `data-upgrade\index.json` 的 `LastWriteTime`。
2. **同一个人**在**同一个群**连发两条消息（第二次绑定值不变）。
3. 期望：`LastWriteTime` 只在**第一条**之后变，第二条之后**不动**。

```powershell
Get-Item .\data-upgrade\index.json | Select-Object LastWriteTime
```

**判据**：第二条消息之后 `LastWriteTime` 不动 ⇒ 通过；动了 ⇒ 比较没生效（回对齐卡 #5 的口径）。

## 5. 回归（对齐卡 #7）：投票块缺 `chat_id` ⇒ 不豁免、不算票

**为什么**：`exempt()` / `accept()` 里的 `or state.get("group_chat_id")` 回退已拆掉（**已落地 `ceaf62a`**，测试 = `test_a_window_block_without_chat_id_neither_exempts_nor_counts`）—— 留着等于让全局单值继续对投票生效。

**单测（主判据）**

- 用缺 `chat_id` 的投票块 ⇒
  - `vote.exempt("2", inbound, state, roster)` 返回 **False**；
  - `vote.accept(...)` **不算票**（回退不再兜到底）。
- 反向对照：块里**有** `chat_id`（正常开窗路径）⇒ 行为与升级前一致（花名册成员 + 纯数字 ⇒ 豁免）。

**手工步（可选）**：正常开窗 → 群里发裸数字 ⇒ 计票（这条本来就归 §4.6 格 B）。

**两条投票口径（PM 2026-09-16 核代码后补；代码 = `src/gateway/vote.py` 的 `_threshold()` / `read_window()`）**

- **要落定就得 ≥2 人投票**：门槛 = `ceil(花名册人数 / 2)`，且还要「某方向已投票者过半」（当前花名册 3 人 ⇒ 门槛 2）。只投 1 票**不会自动收口**，只能等 10 分钟超时（`VOTE_TTL`）或 `封盘`。
- **分母是实时花名册 ⇒ 本清单期间花名册必须冻结**：中途有人登记进来门槛就变（3 ⇒ 2、4 ⇒ 2、5 ⇒ 3）。§0 的丙 / 乙**别在投票测到一半时加进群**。

**顺序纪律（2026-09-16 穿透批踩出来的，做这一格前必读）**

1. **裸数字必须先有窗**：窗关着时裸数字静默是「没窗」的必然结果，与成员资格无关 —— 拿它当证据就是假阳性。
2. **摘花名册成员会同时改分母**：D-36 门槛 = 已投票人数 ≥ `ceil(花名册人数 / 2)`，分母是**当时的花名册人数**。
   2 人花名册下 **1 票即结算**（实测 `过半：1/1 票`），窗会被立刻关掉。所以验「非成员裸数字应静默」时，
   顺序必须是 **非成员先发（应静默）→ 成员后发（应计票、随即结算）**；反过来窗先结算，非成员那条又变成假阳性。
3. 没有第三方账号时，可用**临时摘花名册成员**造出「非成员」：
   `& D:\rehearsal-logs\roster_toggle.ps1 -Drop ou_…` → 测完 `-Restore`
   （还原点 `members_restore_point.json`，还原是字节级回原哈希；只碰 `data-upgrade\members.json`）。


**判据**：缺 `chat_id` 一律**不豁免**（宁静静默）；有 `chat_id` 时与升级前一致。
